Infrastructure as Code (IaC)

📝

Infraestrutura Definida como Código

Princípios do IaC:

  • ✅ Declarativo - Descreve o estado desejado
  • ✅ Versionável - Guardado em Git
  • ✅ Reproduzível - Mesmo código = Mesma infra
  • ✅ Automatizado - Deploy via CI/CD
  • ✅ Testável - Validação antes do deploy

Benefícios:

  • 🚀 Deploy rápido e consistente
  • 📋 Documentação sempre atualizada
  • 🔄 Rollback fácil
  • 👥 Colaboração via pull requests
  • 💰 Redução de custos operacionais

O que é Terraform?

🏗️

Ferramenta Open Source de IaC da HashiCorp

Características Principais:

  • 🌍 Multi-Cloud - AWS, Azure, GCP, +300 providers
  • 📝 Declarativo - Define o "o quê", não o "como"
  • 🔍 Plan & Apply - Preview antes de aplicar
  • 📊 State Management - Rastreia recursos criados
  • 🧩 Modular - Reutilização de código
  • 🔓 Open Source - Comunidade ativa

Por que Terraform?

Líder de mercado em IaC, suporta múltiplos providers, sintaxe simples (HCL), grande ecosistema de módulos oficiais e da comunidade.

A HashiCorp foi adquirida pela IBM, em um negócio avaliado em USD 6.4 bilhões.

Terraform vs Outras Ferramentas IaC

Ferramenta Tipo Cloud Support Linguagem
Terraform Declarativo Multi-cloud HCL
ARM Templates Declarativo Azure only JSON
CloudFormation Declarativo AWS only YAML/JSON
Ansible Procedural Multi-cloud YAML
Pulumi Declarativo Multi-cloud TypeScript/Python/Go
💡 Quando usar Terraform: Projetos multi-cloud, necessidade de modularização, equipas que preferem DSL (domain specific languages) sobre programação completa.

HCL - HashiCorp Configuration Language

Sintaxe Básica:

# Comentário # Bloco de recurso resource "tipo" "nome" { propriedade = "valor" numero = 42 booleano = true lista = ["a", "b", "c"] mapa = { chave = "valor" } # Bloco aninhado configuracao { opcao = "valor" } } # Referência a outro recurso referencia = tipo.nome.atributo

Tipos de Blocos:

  • resource - Define recursos de infraestrutura
  • data - Busca informações existentes
  • variable - Define variáveis de entrada
  • output - Define valores de saída
  • locals - Define valores locais

Variables - Tornando Código Reutilizável

Terraform State

📊

Mapeamento entre Código e Infraestrutura Real

O que é State?

  • Ficheiro JSON que rastreia recursos criados
  • Mapeia configuração para recursos reais
  • Armazena metadados e dependências
  • Crítico para operações do Terraform

Comandos de State:

# Listar recursos no state terraform state list # Ver detalhes de recurso terraform state show azurerm_resource_group.main # Remover recurso do state (não deleta) terraform state rm azurerm_resource_group.main # Mover/renomear recurso terraform state mv azurerm_resource_group.old azurerm_resource_group.new # Pull/Push state terraform state pull > backup.tfstate
14 / 30

Remote State - Colaboração

Problemas do State Local:

  • ❌ Não permite colaboração
  • ❌ Pode ser perdido
  • ❌ Sem locking
  • ❌ Segredos em texto plano

Configurar Remote State (Azure):

# backend.tf terraform { backend "azurerm" { resource_group_name = "rg-terraform-state" storage_account_name = "stterraformstate" container_name = "tfstate" key = "prod.terraform.tfstate" } }

Benefícios:

  • ✅ State compartilhado
  • ✅ Locking automático
  • ✅ Encriptação
  • ✅ Versionamento

Import - Recursos Existentes

Importar Infraestrutura Existente:

# 1. Escrever configuração para match resource "azurerm_resource_group" "existing" { name = "rg-already-exists" location = "South Africa North" } # 2. Importar resource $ terraform import azurerm_resource_group.existing \ /subscriptions/xxx/resourceGroups/rg-already-exists # 3. Verificar state $ terraform state show azurerm_resource_group.existing # 4. Ajustar configuração se necessário $ terraform plan # Deve mostrar: No changes
⚠️ Importante: Import não gera configuração automaticamente. Você precisa escrever o código HCL manualmente.

Best Practices

✅ Fazer

  • Usar remote state sempre
  • Versionar providers
  • Criar módulos reutilizáveis
  • Tags em todos recursos
  • terraform fmt antes de commit
  • Code review em PRs
  • Separar por ambiente
  • Documentar módulos

❌ Evitar

  • Hardcode de valores
  • Segredos em código
  • State local em produção
  • Módulos muito grandes
  • Ignorar terraform plan
  • Force unlock sem investigar
  • Destruir sem backup
  • Editar state manualmente

Estrutura de Projeto Recomendada:

project/ ├── environments/ │ ├── dev/ │ ├── staging/ │ └── prod/ ├── modules/ │ ├── networking/ │ ├── compute/ │ └── database/ └── global/ └── terraform.tf

Segurança em Terraform

🔒 Gestão de Segredos:

Nunca fazer:

# ❌ NUNCA FAZER ISTO! resource "azurerm_postgresql_server" "main" { administrator_password = "MyPassword123!" # NUNCA! }

✅ Boas Práticas:

# Usar Azure Key Vault data "azurerm_key_vault_secret" "db_password" { name = "db-password" key_vault_id = azurerm_key_vault.main.id } # Usar variável sensível variable "db_password" { type = string sensitive = true } # Gerar passwords aleatórias resource "random_password" "db" { length = 32 special = true }

Troubleshooting Comum

🔍 Problemas Frequentes:

State Lock

Erro: "Error acquiring the state lock"

# Verificar quem tem lock terraform force-unlock LOCK_ID # ⚠️ Usar com cuidado!

Drift Detection

Mudanças manuais fora do Terraform

# Detectar drift terraform plan -refresh-only # Atualizar state terraform apply -refresh-only

Debug Mode:

# Ativar logs detalhados export TF_LOG=DEBUG export TF_LOG_PATH=terraform.log terraform plan
